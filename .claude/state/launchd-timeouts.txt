# Per-label timeout bounds for launchd jobs wrapped by bin/launchd_run_record.sh
# (llm#1190 — enforcement half; the reporting half, "High-tier jobs missing a
# declared timeout", lives in .claude/scripts/launchd_health_report.R Section 7
# and reads .claude/state/launchd-timeout-exempt.txt for recorded exemptions).
#
# Policy (decided 2026-09-13, llm#1190): every scheduled job declares a
# timeout unless there is an explicit recorded reason not to (see the
# exemption file). A label with NO entry here runs UNBOUNDED, exactly as
# before this file existed — this is the normal, safe default for a job not
# yet analysed, never a silent claim that it has been bounded.
#
# Format: one entry per line —
#
#   <launchd Label><whitespace><seconds><whitespace># <reasoning>
#
# Comment-stripped/trimmed the same way launchd_health_report.R's
# read_timeout_exemptions() parses launchd-timeout-exempt.txt: everything
# from the first unescaped '#' to end of line is discarded (it is free-text
# reasoning here, not a required field), blank lines and pure-comment lines
# are skipped. Only the first two whitespace-separated tokens on a line are
# read (label, seconds) — bin/launchd_run_record.sh's lookup_timeout_seconds()
# ignores everything after the second token.
#
# ── How these bounds were derived ────────────────────────────────────────────
#
# Source: ~/.claude/logs/launchd_runs.duckdb, table `runs` (label,
# started_at, finished_at), queried read-only. Per llm#1190's own explicit
# instruction, MAX duration is never used as the bound — the maxima are
# contaminated by exactly the hangs this file exists to stop (e.g.
# com.claude.overnight-self-review-email: 28,676s max vs 20s median;
# com.claude.cron-catchup: 36,862s max vs 0s median). Two derivation methods
# were used, chosen per label's actual distribution shape (verified by
# inspecting each label's top-N durations individually, not assumed):
#
#  (A) p95 x 5, rounded UP to the next whole minute, floor 60s. Used for
#      every label below whose top few durations show a SINGLE sharp outlier
#      (one hang, days/weeks apart from the rest) sitting well clear of an
#      otherwise tight, well-behaved p95. With n=42 typical daily-cron sample
#      sizes, p99 sits only ~0.4 points from the maximum and would just
#      re-import the max-contamination problem this file exists to avoid —
#      p95 is the highest percentile that stays clear of a single-run outlier
#      at these sample sizes. 5x is deliberately generous headroom on top of
#      that, not a tight fit.
#  (B) Observed legit/hang gap. Used only for com.claude.cron-catchup, whose
#      distribution is NOT single-outlier-shaped: 8 of 3,402 runs fall
#      between 300-3600s (network/DNS-wait retries — this job already
#      declines to run via a `deferred` status handled elsewhere, see
#      wait_for_resolvable_host.sh) and exactly 2 runs exceed 3600s (36,862s
#      and 13,935s — true hangs). The bound is set at the clean gap between
#      those two clusters (3600s = 1h), which the p95 formula would have
#      gotten wrong (its own p95 is ~1s, since >99% of runs are near-
#      instant and the 5-30min network-wait tail is a small minority).
#
# Every label below was individually verified this way before being added —
# none is a guess. See the PR that introduced this file for the full
# per-label table (n, median, p95, max, chosen bound, method).
