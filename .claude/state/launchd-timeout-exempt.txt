# High-tier launchd job timeout exemptions — read by
# launchd_health_report.R's read_timeout_exemptions() (llm#1187 defect 3).
#
# User decision (llm#1187, 2026-09-13): every launchd job must declare a
# `TimeOut` in its plist unless the plist owner has recorded an explicit
# reason not to, here. A High-tier job with no declared timeout and no
# entry in this file is reported as a FINDING in the weekly health report's
# "High-Tier Jobs Missing a Declared Timeout" section — not merely a blank
# "—" cell in the inventory table.
#
# Format: one entry per line —
#
#   <launchd Label>  # <reason this job is exempt from the timeout rule>
#
# The reason after '#' is REQUIRED — it is read and shown verbatim in the
# report next to the job's label ("exempt: <reason>"), never discarded.
# Lines starting with '#' in the first non-blank position are pure
# comments and are skipped entirely. Blank lines are ignored.
#
# This file is parsed the same comment-stripping/trim way as
# .claude/state/confidential-repos.txt's _confidential_entries() (strip
# from the first unescaped '#' to end of line, trim, skip blank) — except
# here the text after '#' is the exemption's REASON, not documentation to
# discard.
#
# A missing file is the normal case (nothing exempted yet) — every
# High-tier job with no timeout is reported as a finding. Adding a timeout
# to the plist itself is almost always the right fix; use this file only
# when there is a genuine, stated reason the job cannot declare one (e.g.
# it is itself the timeout-supervision mechanism for other jobs).
#
# No High-tier findings are exempt here yet — every High-tier job that could
# take a bound now has one, in .claude/state/launchd-timeouts.txt (llm#1190).
# The two entries below are resident daemons: classify_tier() currently
# scores them "Low" (RunAtLoad, no calendar/interval schedule, no keyword
# match), so neither would render as a High-tier finding anyway — they are
# recorded here regardless, per llm#1190's own instruction ("whatever cannot
# take a bound ... goes in the exemption file with a real reason"), so the
# exemption is documented rather than left to be re-derived from the plists
# by a future reader.

com.roborev.daemon  # Resident KeepAlive+RunAtLoad daemon (no calendar/interval schedule) — it IS the process other roborev CLI operations talk to, so a wall-clock timeout on the daemon itself would make no sense (there is no single "run" to bound). It does not go through bin/launchd_run_record.sh at all (its plist calls roborev_daemon_launcher.sh directly). If it hangs: the `roborev` CLI's own client commands (review/fix/close) would stall or fail against it, Section 5 of the weekly health report ("Stale/Wedged Processes") would flag any wedged `timeout`-wrapped child process it spawns, and ~/.claude/logs/roborev-daemon.log going stale is directly observable. See the 2026-08-13 restart-verification incident (llm#936) for why `launchctl kickstart`'s own exit code is NOT sufficient evidence this daemon actually restarted.

com.roborev.auto-refine  # Resident KeepAlive+RunAtLoad daemon (no calendar/interval schedule) — same reasoning as com.roborev.daemon above; does not go through bin/launchd_run_record.sh (plist calls roborev_auto_refine.sh directly). If it hangs: new roborev findings stop being auto-fixed and the backlog grows silently. Detection: roborev_project_backlog.sh's weekly aggregation would show a rising open-finding count, roborev_agent_health.sh already monitors agent availability, and ~/.claude/logs/roborev-auto-refine.log going stale is directly observable.
